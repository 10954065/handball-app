# HMMS - Database Schema

SQLite 3 (WAL journal, `synchronous=FULL`, foreign keys enforced). Schema source:
`src/main/db/schema.ts`. Migrations: `src/main/db/migrations/*.sql` (generated by drizzle-kit,
reviewed, bundled into the app and applied in order inside transactions; recorded in
`__hmms_migrations`). A failed migration stops the application from starting.

## Principles

1. **Immutable identifiers.** UUID primary keys. Players also get a permanent human-readable
   registration number (`registration_no`).
2. **Snapshots for history.** A match references the match sheet (`match_rosters`,
   `match_team_officials`, team names/colours on `matches`, rules on `matches.rules`). Editing a
   club roster, transferring a player or changing competition rules never alters a played match.
3. **Event ledger is authoritative.** `match_events` is append-only. Mistakes are corrected by
   voiding (`status='voided'`, who/when/why) and inserting a replacement (`replaces_event_id`).
   Every change is written to `audit_logs` in the same transaction.
4. **Derived caches are not truth.** `standings`, `player_statistics`, `team_statistics` and the
   result fields on `matches` are rebuilt from the ledger.
5. **Idempotency.** `match_events.client_request_id` is unique per match, so an accidental double
   click cannot record the same event twice.

## Tables

| Table | Purpose |
| --- | --- |
| `users` | Local accounts. scrypt hash, role, active flag. Unique lower(username). |
| `media` | Team logos and player photos as BLOBs (backup = one file). |
| `teams` | Team identity, colours, staff, logo, captain and primary goalkeeper. |
| `players` | Player identity and registration data. |
| `team_players` | Registration history. Partial unique indexes: one active jersey number per team, one active team per player (`left_at IS NULL`). |
| `venues` | Venues. |
| `officials` | Referees, delegates, timekeepers, scorekeepers. |
| `competitions` | Competition, format, rules, points system, tie-breakers. |
| `seasons` | Editions of a competition. |
| `season_teams` | Teams registered in a season, with group. |
| `matches` | Fixture/match: teams, venue, schedule, stage, status, rule and team snapshots, cached result. |
| `match_officials` | Officials assigned to a match (name snapshot). |
| `match_lineups` | Per-side lineup confirmation (who, when). |
| `match_rosters` | Match sheet snapshot of each player: jersey, name, position, photo, GK/captain/starter flags. |
| `match_team_officials` | Team officials A-D on the match sheet. |
| `match_clock` | Persisted clock state: phase, period, base ms, run start (wall and monotonic), owning process id, checkpoint. |
| `match_periods` | Period records: kind, start/end, score at end. |
| `match_events` | The ledger (shots, sanctions, time-outs, substitutions, period markers). |
| `suspensions` | One row per suspension/disqualification reduction (mirrors the ledger, for reporting). |
| `substitutions` | Substitution history (mirrors the ledger). |
| `timeouts` | Team time-outs with wall-clock start/end. |
| `standings` | Derived standings cache per season and group. |
| `player_statistics` | Derived per-match player statistics cache. |
| `team_statistics` | Derived per-match team statistics cache. |
| `match_reports` | Archive of generated PDF/XLSX reports. |
| `app_settings` | JSON application settings. |
| `audit_logs` | Append-only audit trail (who, what, before, after). |
| `backup_history` | Every backup: path, size, SHA-256, integrity result. |

## Conventions

- Timestamps: integer milliseconds since the Unix epoch (UTC). Dates of birth: `YYYY-MM-DD`.
- Booleans: INTEGER 0/1.
- JSON columns: `rules`, `tiebreakers`, `app_settings.value`, `audit_logs.before/after`.
- `ON DELETE RESTRICT` protects anything referenced by historical matches (teams, players,
  match rosters). Records are archived, not deleted.

## Backup and restore

- Backups use the SQLite online backup API through the live connection, so committed data still
  in the WAL is included. Each backup is re-opened read-only, `integrity_check`ed and hashed.
- Restore verifies the candidate first, creates a verified `pre_restore` backup, closes the
  database, swaps the file atomically, removes stale `-wal`/`-shm` files and reopens (running
  pending migrations). If reopening fails, the pre-restore copy is put back.
